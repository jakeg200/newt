# M2 — Capture and cases

**Status:** built 2026-10-17 on branch `m2-capture`. 84 backend tests pass; the web app type-checks
and lints clean; the Capture screen was run by hand against the live API.

## Acceptance

| Criterion | Result |
| --- | --- |
| 20 of 20 test items become cases | Met. The 20-invoice test mailbox gives 20 cases; a duplicate upload of one message doesn't make a 21st. |
| ≥95% of mentor actions matched | Met: 20 of 20 (100%), each to the right item, with no wrong matches. 16 matched by reply headers and 4 by invoice number alone (no threading headers). Two decoy emails correctly stay unmatched: one unrelated, one naming a PO that two invoices share. |
| No message bodies in logs | Met. A test captures every log record at DEBUG during import and checks that no body text, reply text or personal data appears. SQLAlchemy's parameter logging is pinned off. |

Also checked: nothing raw is stored. Snapshots, actions and match keys are scanned for the
fixture's emails, phone numbers and bank details.

## Built

- **Sources** (`app/capture/sources/`): `.eml`/`.mbox` upload; Gmail (read-only scope, one label,
  whole threads so the mentor's replies in Sent are included); CSV/JSON with a column map; a REST
  push endpoint with a per-connection token (stored hashed, shown once).
- **Redaction** (`app/capture/redact.py`): emails, phone numbers, IBANs, cards (Luhn-checked), sort
  codes, account numbers and NI numbers become stable pseudonyms such as `[EMAIL 3fa9c1]`, keyed by
  `APP_SECRET`. Invoice, PO and ticket numbers survive. Quoted history is stripped from replies.
- **Match keys** (`app/capture/keys.py`): message ids, thread ids and addresses are kept only as
  keyed hashes; reference tokens come from redacted text.
- **Matcher** (`app/capture/matcher.py`): explicit reference, then reply headers, then same thread,
  then a unique shared reference number within 60 days. It never matches an item that arrived
  after the action, and leaves ties unmatched rather than guessing.
- **Decisions** come from a `capture` section in each task-type config (for example, a reply to the
  sender means `query_supplier`, a forward means `escalate`, status "approved" means `approve`).
  The mentor's reply text becomes the task's text output.
- **Waiting actions**: an action whose item hasn't arrived yet is kept, redacted and hashed, and
  retried whenever new cases arrive. Upload order doesn't matter.
- **Consent and control**: email capture needs the mentor's consent (recorded in `consents`).
  Connections can be paused, and deleting one deletes every case it captured. Only the mentor
  (or an admin) sees captured cases.
- **API**: `/connections` (create, list, patch, delete, import, sync, OAuth start, runs, unmatched),
  `/oauth/google/callback`, `/capture/push/{id}`, `/cases`, `/cases/{id}`.
- **Web**: Capture screen with connections, run reports, waiting actions, a cases table and a case
  drawer.
- **Samples** (`samples/capture/`, regenerate with `scripts/make_sample_capture.py`): the test
  mailbox and a ledger CSV with its column map.

## Left for later

- Gmail is tested against a mocked Google only. A real run needs a Google OAuth client
  (see NEEDS_JAKE.md) and a test mailbox.
- Outlook (Microsoft Graph) isn't built yet; Gmail, uploads, CSV and REST cover the first design
  partners.
- Gmail label changes (for example "Approved" applied with no reply) aren't captured as actions,
  because Gmail doesn't timestamp label changes. Approvals come from CSV, REST or status pushes.
- Redaction is pattern-based. Personal names in free text aren't redacted; add a name detector
  before real customer data if a design partner's data needs it.
- Gmail sync is manual ("Sync now"). Scheduling moves to the jobs worker with live shadowing (M5).
